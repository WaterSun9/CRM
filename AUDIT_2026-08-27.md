# Watersun CRM — Development and User-Risk Audit

Date: 2026-08-27

## Executive verdict

The application builds successfully and the main admin list already paginates in groups of 50, so 5,000 rows alone is not the central risk. The release is **not ready for 30 simultaneous users across eight roles** until the critical authorization paths and data-loss behavior are fixed and tested.

The user's concern about lost work is valid. The main customer editor clears its dirty state and reports success before Supabase confirms the write, while the Add Lead form can be closed with no warning or draft recovery.

## P0 — block release

### 1. Vendor email Edge Function can expose any customer's data

`supabase/functions/send-lead-to-vendor/index.ts` uses the service-role key, accepts an arbitrary `customer_id` and destination email, and never verifies the caller or record ownership. Disable this function until it authenticates the caller, authorizes the requested customer, and resolves the destination from trusted server data.

### 2. Agent role can potentially reset another user's password

`supabase/functions/add_user/index.ts` treats any role containing `partner` as privileged. The documented ordinary agent role is `Channel Partners`. The `update_password` branch does not perform the ownership restriction used by some other actions. Use an exact privileged-role allowlist and restrict password resets to admins.

### 3. Documented RLS grants all authenticated users access to all customer rows

`Requirements.md` says all authenticated users may select, insert, and update `admin`. Client-side filters do not provide authorization. If this documentation matches production, any authenticated role can bypass the UI and access another role's customers. Export the live policies, place them in migrations, and create allow/deny tests for every role and operation.

### 4. Save can look successful before the database write succeeds

`CustomerDetailModal.jsx` clears `isFormDirty`, sets saved state, and stops the spinner before the background `onUpdate` finishes. The dashboard's update handler catches errors internally, so the caller may still resolve. Await the database result, verify one returned row/version, keep dirty state on failure, and only show success after confirmation.

### 5. Concurrent editors silently overwrite each other

Customer save and stage change send almost the complete customer snapshot. Two users editing different fields from stale copies will produce a last-write-wins overwrite. Send field-level patches and add optimistic concurrency using `updated_at` or a version column; show a conflict dialog with refresh/merge choices.

## P1 — fix before a 30-user rollout

### Unsaved-work protection

- `AddLeadModal.jsx` closes from X or Cancel without checking whether the user entered data.
- The main customer modal warns only for its own close button and tab switch. There is no `beforeunload` protection for refresh, browser close, route change, logout, or update-check reload.
- Several section-level drafts never mark the parent form dirty at all: new loan/subsidy entries, stamp resend remarks, activity notes, bulk panel-serial paste, and document remarks. Those can disappear without even triggering the modal's existing warning.
- Agent and Vendor portals protect only selected tabs/actions; closing the customer, returning to the dashboard, or logging out can bypass their dirty checks.
- There is no recoverable draft for a new lead or in-progress customer edit.
- Document upload failures during lead creation are logged but the form closes as if everything succeeded.

Recommended behavior:

1. Keep a real dirty state based on changed values, not merely opening an editor.
2. Guard modal close, Cancel, tab/stage navigation, app navigation, logout, and browser unload.
3. Autosave a local draft every 1–2 seconds, keyed by user + customer/form, and show `Draft saved locally` with a timestamp.
4. Clear the draft only after a confirmed Supabase write.
5. On return, offer `Restore draft` and `Discard draft`.
6. Treat partial document upload as a recoverable incomplete state, with per-file retry.

### Realtime request amplification

Every Dashboard client subscribes to every `admin` change. Each event triggers the metrics RPC, metadata query, and delivery-batch count. With 30 dashboard users, one write can cause about 30 callbacks and up to 90 follow-up queries. Filter Realtime server-side, coalesce metrics refreshes, and consider Broadcast for scalable role/topic delivery.

### Full-table and repeated fetching

Agent, Vendor, Stamp, Delivery Batch, and Installation Payment views fetch broad `select('*')` datasets. Vendor polling repeats every 15 seconds; Stamp also performs an N+1 document query. Replace with server-filtered, column-limited cursor pagination and lazy detail/document loading.

### Multi-row operations are not atomic

Delivery batch assignment updates customers sequentially and can leave a partially applied batch. Move batch + project assignment into a single checked database transaction/RPC with idempotency.

### Fail-open role/session behavior

- A missing or failed profile fetch falls back to `sales`, a privileged dashboard role. Fail closed.
- Deactivation updates profile state but does not immediately revoke/deny an existing session. Enforce active status in authorization/RLS for sensitive operations.
- Vendor name matching can treat generic `vendor` text as a match for unrelated assigned records.
- Role fields may be self-editable if the documented own-profile UPDATE policy is unrestricted by column.

## P2 — important quality and accessibility work

- Global search omits the stated `deleted_at is null` filter.
- Offset pagination can skip or duplicate records during concurrent inserts; use keyset ordering on `(created_at, id)`.
- File names based on `Date.now()` plus original name can collide during simultaneous uploads, and `upsert: true` may overwrite a file. Use UUIDs.
- The login inputs rely on placeholders rather than visible labels; the password-visibility button has no accessible name. Text and controls are unusually small at desktop width.
- Lint completes with 0 errors but 107 warnings, including stale/missing hook dependencies in live data flows.

## Capacity test plan

Seed 5,000 realistic `admin` rows, including large JSON/history fields and documents. Run 30 authenticated clients distributed across all eight roles.

Required gates:

- p95 initial list load under 2 seconds and p95 filtered search under 500 ms on the target network.
- No unauthorized row returned or writable for any cross-role/partner test.
- Two-session concurrent edit test preserves both independent changes or produces an explicit conflict.
- Offline/slow-network Save never displays success before confirmation; refresh/close restores the draft.
- Realtime at 1–5 writes/second does not produce unbounded metrics-query fanout or visible lag.
- 100-project delivery batch either commits fully or rolls back fully under an injected failure.
- Upload failure and duplicate-file tests provide retry without false completion.
- Run `EXPLAIN (ANALYZE, BUFFERS)` against production-like data and validate indexes supporting stage/partner/vendor/deleted filters, stable creation ordering, and document customer lookup.

## Recommended implementation order

1. Disable/fix the unauthenticated vendor-send function and the password-reset privilege path.
2. Export and test live RLS/grants for all eight roles; make the schema reproducible in migrations.
3. Make Save awaited and verifiable; add field patches plus conflict detection.
4. Add close/navigation/unload guards and recoverable drafts to Add Lead and customer editing.
5. Filter/coalesce Realtime and paginate all broad portal queries.
6. Make batch/document workflows transactional or explicitly recoverable.
7. Run the 30-client/5,000-row acceptance suite before rollout.

### Document send-back security follow-up

The current UI supports the basic workflow: Agent/Agent 2/Channel Partner users cannot freely change or delete an uploaded document; Admin or Office can mark it **Send Back**, after which that one document can be replaced and becomes locked again.

Before production rollout, replace the temporary remark-based marker with dedicated Supabase document review fields such as `review_status`, `review_remark`, `reviewed_by`, and `reviewed_at`. Add RLS policies that enforce:

- Only Admin and Office can approve or send back documents.
- Agents and Channel Partner users can replace only documents whose status is `sent_back`.
- A successful replacement clears the send-back state and locks the new document.
- Upload the replacement successfully before deleting the old file, so a failed upload cannot destroy the existing document.

Add this database/RLS work immediately after fixing the profile role constraint and test it with real authenticated accounts for every affected role.
